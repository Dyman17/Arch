## 🌳 Git-workflow (обязательно)

### Ветки

```
main            ← только через PR + ревью техлида, НИКОГДА не писать напрямую
 ├── feature/<задача>   ← фича (login, dashboard, api...)
 ├── fix/<что-то>       ← багфикс
 └── docs/<что-то>      ← только документация
```

### Цикл работы над задачей

```bash
# 1. Взять задачу — из docs/tasks.md, согласовать с техлидом
# 2. Свежая ветка от main:
git checkout main
git pull origin main
git checkout -b feature/название-задачи

# 3. Работать — мелкие коммиты с понятными сообщениями
git add .
git commit -m "feat: add login form"   # или fix:/docs:/chore:

# 4. Перед каждым коммитом — подтянуть main
git pull origin main

# 5. Запушить и открыть PR
git push origin feature/название-задачи
gh pr create --fill

# 6. Дождаться ревью техлида → он мержит
gh pr merge --squash   # делает ТЕХЛИД, не ты
```

### Правила PR

- PR = одна задача, не смешивать 5 фич в одном PR
- Название: `feat: ...`, `fix: ...`, `docs: ...`
- Описание: что сделано, как проверить
- Скриншот/GIF для UI-изменений — обязательно
- **Свой PR мержить самому запрещено**

## 🚫 Запрещено (нарушение = откат)

- Писать/форсить в `main` напрямую
- Мержить свой PR без ревью техлида
- Коммитить `.env`, ключи, токены, пароли
- Удалять/переписывать чужие коммиты (`git push --force` в общих ветках)
- Большие коммиты на 500+ строк без объяснения в PR
- Начинать большую фичу без задачи в `docs/tasks.md`

## 🎯 Как подходит к работе ИИ-агент

Когда тебя (агента) просят сделать задачу:

1. **Прочитай** `docs/tasks.md` — какая задача, её статус, её ветка
2. **Прочитай** связанные флоучарты в `docs/` — не изобретай архитектуру, следуй документации
3. **Если архитектура/стек неясны** — остановись и спроси техлида, не гадай
4. **Работай в своей ветке**, не переключайся на `main` для изменений
5. **Коммиты — мелкие и по делу**: `feat: ...`, `fix: ...`, не «wip» и не «update»
6. **Обнови статус задачи** в `docs/tasks.md` (⬜ → 🔄 → ✅)
7. **Открой PR** и напиши, что сделано и как проверить
8. **Жди ревью техлида** — не мержи сам

### Скоуп разработчика

- **Backend-агент**: `backend/`, API, БД, миграции, тесты бэка. Не трогай UI-компоненты.
- **Frontend-агент**: `frontend/`, страницы, компоненты, стили. Не ломай API-контракт — если нужен новый эндпоинт, задача в `docs/tasks.md` + согласование с бэком/техлидом.

### Контракт между фронтом и бэком

- Эндпоинты и формат данных фиксируются в `docs/api-flow.md` **до** кода
- Менять контракт можно только через техлида
- Фронт не придумывает эндпоинты, бэк не меняет их молча

## 🔄 Синхронизация команды

- Каждые 2–3 часа: `git pull origin main`, статусы в `docs/tasks.md`
- Блокер > 15 минут → писать техлиду, не сидеть в тишине
- Техлид периодически мержит проверенные PR в `main`

## 📋 Работа с задачами (`docs/tasks.md`)

| Поле | Кто заполняет |
|------|---------------|
| Задача, ветка, исполнитель | Техлид при разборе кейса |
| Статус ⬜→🔄→✅ | Исполнитель (или его ИИ-агент) |
| Новая задача из работы | Согласовать с техлидом, потом добавить |

Берёшь задачу → сразу меняй статус на 🔄, чтобы второй разработчик не взял ту же.

## ✅ Definition of Done

Задача считается готовой, когда:

- [ ] Код в отдельной ветке, запушен
- [ ] `git pull origin main` проходит без конфликтов
- [ ] Функция работает локально (ручная проверка)
- [ ] Статус в `docs/tasks.md` = ✅
- [ ] PR открыт, описание заполнено
- [ ] Ревью техлида пройдено → замержено

## 💡 Принцип

> **Качественно и точно по одной идее — лучше, чем «дтофига идей» и хуй пойми что.**

Документация в `docs/` — источник истины. Код следует документации, а не наоборот.
